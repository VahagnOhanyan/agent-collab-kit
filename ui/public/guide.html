agent-collab-kit — руководство разработчика

Сверено с релизом 88874f9, 3 октября 2026. Файл лежит в репозитории набора: ui/public/guide.html.

Что это

agent-collab-kit — машинный набор, который позволяет нескольким AI-агентам (Claude Code, Codex, Gemini, Cursor и другим) работать над одним проектом как команда. Один агент — ведущий: в нём работает человек, он планирует и раздаёт работу. Остальные берут задачи и ревью через общий журнал. Набор ставится один раз на машину и действует во всех её проектах.

Что он даёт на практике:

  • Общий журнал collab — задачи, ревью, решения и одобрения владельца лежат в файлах, а не в контексте одного агента. Его видит любой агент через MCP и человек через CLI и веб-панель.
  • Правила работы — план до первой правки, уровни сложности L0–L3, кто кого проверяет, словарь терминов до начала задачи. Ставятся каждому агенту в его формате.
  • Хуки-ограничители — не дают сделать то, что правила запрещают: вызвать субагента без явной модели, править код без плана, пушить мимо гейта, писать вне разрешённых путей.
  • Субагенты и скиллы — implementer (пишет только в разрешённых областях), verifier (только читает и гоняет проверки), процедуры handoff, adversarial-audit, ui-review, codex-review, claude-review, ux-guidance и другие.
  • Панель collab ui — страница в браузере: задачи, ревью, состав агентов и мастер настройки.

В наборе не зашит ни ведущий, ни вендор. Каталог только описывает, что умеет каждый агент. Кто есть у вас и кто в какой роли — ваш состав, его выбирают в мастере.

Устройство

Правки в исходнике ничего не меняют, пока их не закоммитили и не установили: агенты читают ~/.agent-collab-kit/current и копии, разложенные установщиком. Состав и реестр проектов лежат там же, но вне релиза и переживают обновления.

Установка

Установка занимает около 2 минут: установщик сам прогоняет тесты набора и при любом сбое откатывает всё, что успел изменить. Работает на macOS и Windows, на обеих проверено живой установкой.

Нужно заранее: git, Node.js 20.19 или новее, доступ к репозиторию набора (он приватный) и хотя бы один установленный агент — Claude Code, Codex CLI, Gemini (agy) или Cursor.

  1. Склонировать репозиторий в домашнюю папку: ~/agent-collab-kit (Windows: %USERPROFILE%\agent-collab-kit). Проще всего через GitHub Desktop: на странице репозитория Code → Open with GitHub Desktop. Обычный git clone тоже подойдёт, если git умеет входить в GitHub (GitHub Desktop, VS Code или Git Credential Manager).
  2. Запустить установщик из папки набора: на macOS и Linux — ./install.sh, на Windows — дважды щёлкнуть install.cmd.
  3. Открыть новый терминал: старый не знает команду collab. Проверка: collab doctor.
  4. Перезапустить открытые сессии агентов, чтобы они увидели MCP collab, правила и скиллы.
  5. Настроить состав — раздел «Настройка».

Что делает установщик:

Несколько аккаунтов Claude Code. У каждого свой каталог настроек (~/.claude, ~/.claude-account-2), и сессия читает правила только из своего. Дополнительный каталог передаётся флагом --claude-config-dir <путь> (можно повторять) или берётся из CLAUDE_CONFIG_DIR.

Правила не править в установленной копии (~/.claude/rules/…). Изменённая руками копия остановит следующую установку с ошибкой «was not created by this installer». Правится исходник в ~/agent-collab-kit/rules/, дальше коммит и переустановка.

Настройка

Настройка — два шага: один раз на машину выбрать состав агентов и один раз в каждом проекте подключить его.

Состав агентов — мастер панели

Запустите collab ui в своём терминале и откройте «Мастер настройки». Панель записывает только кнопкой «Применить» и только когда запущена из вашего терминала. Состав ложится в ~/.agent-collab-kit/collab/agents.json, вне git.

ШагЧто выбираетеНа что смотреть
1. Кто участвуетГалочки у агентов, найденных на машинеПлашка «без CLI запуска»: такой агент может быть ведущим, но не подчинённым
2. Кто ведущийАгент, в котором вы сами работаетеПредупреждение, если подчинённого ведущий запустить не сможет
3. Режим ревьюcross_vendor или single_vendorС одним вендором ревью делает тот же агент в отдельной сессии на другой, не более слабой модели
4. ЯзыкЯзык текстов, которые агенты пишут вам—
5. РолиКакие роли держит каждый агентКрасные дыры независимости делают «Применить» серой

То же из терминала: collab setup --agents claude,codex --lead claude.

Роли и кто кого проверяет. Роль — это обязанность, а не агент. У рабочих ролей есть ревьюеры, и каждого из них должен держать кто-то кроме автора:

Роль исполнителяКто проверяет
ios_engineer, product_engineer, software_engineercode_reviewer + ux_reviewer
backend_engineer, architect, test_engineercode_reviewer
researcher и сами ревьюерыникто

При двух вендорах дыра (ревьюера держит только автор) — ошибка, при одном — заметка. security_reviewer не требуется никому: его зовёт ведущий сам, когда нужно. То же можно записать без панели: collab setup --agents claude,codex --lead claude.

Ревьюер не может писать — и это держит запуск, а не роль. Роль только говорит, кому поручать ревью; права правки она не отнимает. Поэтому у каждого агента в каталоге записан запуск на ревью (adapter.review_launch) — команда, которой его запускают без права записи, и чем это держится. Роли code_reviewer, ux_reviewer, security_reviewer (признак read_only в roles.json) даются только агенту с таким запуском; без него мастер снимает их с причиной, с непроверенным — оставляет с пометкой.

АгентЗапуск на ревьюЧем держится «только чтение»Проба
Codexскилл codex-review: codex exec -s read-onlyСистемная песочница CodexПройдена 02.10.2026
Claude Codeскилл claude-review: claude -p --tools "Read,Grep,Glob", только журнал collabВ сессии нет инструментов правки и оболочки, настройки и хуки не грузятся, из журнала доступны четыре инструментаПройдена 02.10.2026, включая проект с хуком, пишущим файл
Gemini, Cursorнет—Роли ревьюера недоступны

Ревью по роли делается только этими скиллами, не в открытой сессии агента: у неё есть право правки. Новому вендору запуск на ревью записывают после пробы: агента просят создать файл в пустой папке, и файл не должен появиться. Журнал тоже держит правило: ревью нельзя отправить агенту без роли ревьюера ни по имени, ни по способности, а агент, потерявший роль, не может сдать вердикт по ждущему ревью — его снимает release_review. Проектный roles.json признак read_only с роли ревьюера снять не может.

Предел, о котором надо помнить. Журнал видит, какой агент отвечает на ревью, но не как запущена его сессия. Открытая сессия Claude с правом правки под тем же именем claude технически может ответить. Гарантию держат две вещи вместе: роль ревьюера есть только у агента с проверенным безопасным запуском, и ревью запускается только скиллом (codex-review, claude-review), а не в открытой сессии.

Подключение проекта

В папке проекта, в своём терминале:

  1. collab connect --dry-run — показать, что будет записано.
  2. collab connect — подключить. Делает только человек, агенту эта команда закрыта: запись в реестре выдаёт агентам права.

Реестр проекта лежит в ~/.agent-collab-kit/projects/<id>/, вне репозитория, и читается сразу, без переустановки:

ФайлЧто задаёт
project.jsonid и корень; gate — скрипт проверок перед push; plan_gate — какие пути нельзя править без плана; post_edit — гейты после правки контракта
scopes.jsonКуда может писать implementer
readonly-guard.jsonКакие команды разрешены verifier
collab/*.jsonСвои роли, раннеры, политика; проверка — collab check-config

Личное — свои вендоры, тарифы, лимиты — каждый пишет в personal/rules/personal.md в своей копии набора, вне git. Без него работают только общие правила.

Обновление и откат

Обновление — это та же установка свежего коммита. Машина пользуется установленным релизом ~/.agent-collab-kit/current, а не рабочим деревом, поэтому git pull без установки ничего не меняет.

  1. В папке набора забрать свежий main: git pull или «Fetch → Pull» в GitHub Desktop.
  2. Проверить без изменений: bin/agent-collab-kit-install --dry-run.
  3. Установить: ./install.sh (Windows — install.cmd) или bin/agent-collab-kit-install.
  4. Перезапустить открытые сессии агентов и collab ui, если панель была открыта.
  5. Проверить состав: мастер → «Команда выполнена — проверить». Новый релиз может добавить правило, которому прежний состав не отвечает: панель назовёт его и не даст применить новое, пока дыра не закрыта.

Откат к предыдущему релизу: bin/agent-collab-kit-install --rollback. Установщик в конце каждого прогона печатает точную команду со всеми нужными --claude-config-dir. Релизы лежат в ~/.agent-collab-kit/releases/, старые чистятся сами.

Своя правка набора. Правится исходник, затем тесты, коммит и установка. Тесты:

node --test                                   # журнал и панель
node --test tests/test_*_guard.mjs             # хуки, ~40 с
node --test tests/test_install_*.mjs           # установщик, ~3 мин

Публикация в общий репозиторий идёт только потомком предыдущей публикации, без --force. Перед push проверьте, что в коде нет имён своих проектов, личных данных и ключей.

Как идёт работа

Ведущий пишет план до первой правки, заводит задачу в журнале и адресует её роли, а не имени агента. Исполнитель ставит claim_task и claim_files — дерево общее, чужой живой захват отвергается. Свою же задачу автор не ревьюит: request_review откажет. При одном вендоре ревью делает тот же агент в отдельной сессии на модели не слабее авторской.

Когда пишущих задач несколько, у каждой — своя копия: ведущий делает collab worktree add <task> (git worktree и ветка agent/<task>-<slug>), и внутри этой копии хук claim-guard держит заявку — правка вне claim_files отменяется, пока путь не заявлен; лишнее отдаётся release_files. Пути из списка shared_infra проекта (контейнер DI, сетевой клиент, сессия, схема) фича не заявляет, а просит отдельной задачей с spec.infra_request: true и ждёт её. Аудиты читают один снимок (collab worktree snapshot); задача, которая чинит от более позднего коммита, сначала перечитывает находки по diff и ставит spec.delta_checked_at, иначе claim_files отвечает DELTA_REQUIRED. Готовое вливает ведущий по одной задаче: rebase на main, сборка, целевые тесты, гейт; копии закрытых задач снимает collab worktree gc.

Разногласие двух агентов не решается тем, кто сказал последним: позиции записываются в решение, и закрыть спор может только владелец. Одобрений не выдаёт ни один агент и ни панель: только collab approve в интерактивном терминале владельца.

Что требует слова владельца и почему

Одобрение появляется не потому, что агент так захотел. Когда агент заводит задачу, журнал прогоняет текст её действия через таблицу политики (policy.json) и относит к классу: деньги, прод, удаление, секреты, «наружу» (push, письмо, публикация), правка, чтение. Опасный класс требует одобрения, и задача встаёт в «ждёт владельца».

Действие — это то, что агент будет делать: глагол и объект («fix the frame crop on iPhone Duo», «написать тесты модели»), а не название задачи и не симптом. Действие, которого таблица не узнала, не создаёт задачу: агент получает отказ ACTION_UNRECOGNISED с подсказкой и переформулирует сам; необязательное поле action_kind (read, edit, test, publish, delete, secrets, deploy, pay) заменяет глагол и может только повысить класс. Опасное по словам всё равно идёт владельцу.

Карта файлов

Набор живёт в четырёх местах, и у каждого своя роль. Главное правило: состояние работы — в проекте, настройки проекта — вне репозитория, код набора — в установленном релизе.

Почему реестр проекта лежит вне репозитория: он выдаёт агентам права (куда исполнителю писать, какие проверки запускать). Лежи он в репозитории, агент мог бы выдать их себе сам. Поэтому collab connect делает только человек, а агент может лишь показать --dry-run.

Журнал проекта один на репозиторий: все рабочие копии (worktree) пишут в один .collab/. Задачи одного проекта не видны из другого.

Как набор встречается с проектом

Один раз человек подключает проект, а дальше всё происходит само при каждой сессии агента.

Подключение (один раз, человек в терминале). В папке проекта collab connect --dry-run показывает предложение, collab connect записывает его. Команда смотрит на проект и создаёт в реестре projects/<id>/: project.json (id, корень, гейт, plan_gate, post_edit), scopes.json (куда исполнителю можно писать — все отслеживаемые git папки верхнего уровня, кроме скрытых), readonly-guard.json (группа команд сборки, если в проекте есть Xcode или Swift). И создаёт журнал .collab/ в проекте. Из оболочки агента и без терминала команда откажет.

Каждая сессия агента в проекте:

  1. Агент стартует и читает свои инструкции: у Claude — rules/ из его папки настроек, у Codex — блок в AGENTS.md.
  2. Хуки срабатывают на действиях агента (у Claude они в settings.json): session-start при запуске, model-guard, plan-gate и push-gate перед действием, post-edit после правки. Каждый хук находит настройки проекта по рабочей папке: ищет в реестре проект, чей корень содержит эту папку, и читает его project.json. Нет проекта или настройки — хук молча пропускает.
  3. Запускается сервер журнала (collab/src/mcp/server.mjs) как дочерний процесс агента. Переменная COLLAB_AGENT_ID говорит ему, с кем он разговаривает. Он определяет корень проекта по рабочей папке и открывает .collab/.
  4. Агент вызывает инструменты (create_task, claim_task, request_review…). Сервер отвечает через единый фасад api.mjs: проверяет политику, роли и состояния и пишет в журнал под замком.
  5. Субагенты ограничены отдельно. implementer пишет только в области из scopes.json (хук scope-guard в его описании), verifier ничего не правит и запускает только разрешённые команды (readonly-guard).

Корень проекта один на все рабочие копии (worktree) репозитория, поэтому агент в ветке и агент в основном дереве видят одни и те же задачи.

Слои настроек: что что заменяет

Настройки читаются слоями, и более близкий к проекту слой заменяет более общий. Заменяется файл целиком, а не по ключам.

СлойГдеЧто даёт
1. Проект~/.agent-collab-kit/projects/<id>/collab/*.jsonСвои роли, раннеры, политика, состав (agents.json) и инструкции для этого проекта
2. Машина~/.agent-collab-kit/collab/agents.jsonСостав: кто есть, кто ведущий, роли
3. Встроенноеcurrent/collab/config/*.jsonКаталог агентов, роли, способности, политика, модели, раннеры

Что проект изменить не может (набор отвергает или молча игнорирует):

  • Политика (policy.json): проект может добавить классы и правила, но не убрать и не ослабить встроенные; добавленное правило не может быть мягче класса «не узнал». Ослабление требует явной пометки и обоснования.
  • Роли ревьюера: признак read_only у code_reviewer, ux_reviewer, security_reviewer вернётся на место, даже если проектный roles.json его не содержит.
  • Адаптеры агентов (как запускать): берутся только из встроенного каталога.
  • Модели и уровни (models.json): только встроенные, проектная копия игнорируется с предупреждением.

Из репозитория проекта настройки не читаются вообще: ни раннеры, ни политику, ни состав он подсунуть не может. Это граница, ради которой реестр лежит вне репозитория.

Установщик по шагам

Установщик (bin/agent-collab-kit-install) берёт только закоммиченное состояние и ставит его как новый релиз. Каждый шаг, который что-то меняет, записывает в свой журнал, как его отменить: при сбое всё откатывается в обратном порядке.

  1. Проверка источника. Дерево чистое, определён коммит; старая установка под прежним именем переносится.
  2. План. Установщик заранее считает, что будет записано, и отказывает, если на месте копии лежит чужой файл или копию правили руками («was not created by this installer»).
  3. Сборка. git archive коммита → папка releases/<sha>. В ней прогоняются тесты collab (0 падений, пропуск допустим только с причиной platform:) и дымовой тест MCP: сверка списка инструментов и то, что без журнала ничего не создаётся.
  4. Переключение. Ссылка current атомарно переводится на новый релиз.
  5. Раскладка по агентам (следующий раздел): копии правил, скиллов и субагентов, хуки, регистрация журнала, лаунчер collab в PATH.
  6. Учёт и уборка. Запись в history.jsonl, остаются три последних релиза.

Откат к прежнему релизу: bin/agent-collab-kit-install --rollback. Он читает history.jsonl и возвращает current на предыдущий релиз.

--source <папка>Ставить из другого клона
--home <папка>Чужой домашний каталог (для проверок, настоящий аккаунт не затрагивается)

Журнал проекта .collab/

Журнал — это обычные файлы в папке проекта, без базы данных. Его читают и пишут сервер collab (для агентов), CLI и панель (для человека), и все они ходят через один фасад collab/src/api.mjs.

Как пишется. Любое изменение идёт транзакцией (store.transact): берётся замок (файл создаётся с флагом «только если нет», чужой замок определяется по процессу и возрасту), запись проверяет версию записи и откажет, если её успел изменить другой агент, и событие дописывается в ленту. Два агента не затрут правки друг друга: второй получит отказ с просьбой перечитать.

Чего журнал не принимает как журнал: папку .collab/, закоммиченную в репозиторий; журнал, скопированный в другой корень (пока владелец не привяжет его командой init --adopt); .collab/-символьную ссылку; полупостроенный журнал без метки. Это защита от подмены состояния.

Состояния задачи (transitions.mjs): created → assigned → in_progress → review → approved → completed; вбок — waiting_for_user, waiting_for_agent, changes_requested, blocked; конечные — completed, cancelled. Что таблица переходов держит сама, а не просьба в промпте:

  • в in_progress задача попадает только после допуска: если действию нужно одобрение, оно должно быть выдано;
  • в review — только если у задачи needs_review не выключен;
  • completed у задачи с ux_impact: HIGH требует одобренного ревью ux_reviewer;
  • владелец закрывает и возвращает задачи отдельным путём (collab close / reopen, панель), вне таблицы переходов; агентам этого пути нет.

Особенности агентов: как кого запускают

Каталог (collab/config/agents.json) описывает каждого агента полем adapter. Главные слова:

  • kind: manual — сообщение попадает во входящие, агент читает его, когда его сессия работает. kind: cli — слой мог бы запустить программу сам; enabled: false означает, что не запустит. Владелец решил: платный агент сам по событию не стартует.
  • headless — команда, которой другой агент может запустить этого на задачу. Без неё агент может быть ведущим, но не подчинённым: мастер показывает плашку «без CLI запуска». Есть ли команда в PATH, проверяется, а что запуск завершится успехом — нет.
  • cannot — чего программа не умеет в принципе.
  • review_launch — команда запуска на ревью без права записи, с датой, версией программы и доказательством пробы.

Факты машины (probe.mjs) решают, что агент вправе держать именно здесь: программа не найдена, сессия Codex настроена только на чтение, нет запуска на ревью — и мастер снимает соответствующие роли с причиной. Непроверенное оставляет роль с пометкой.

Почему запуск на ревью отдельно: роль ревьюера — это метка для маршрутизации, и право правки она не отнимает. Открытая сессия Claude может править файлы, каким бы ни был её промпт. Удерживает именно способ запуска.

Почему у агентов разные адаптеры

Коротко: адаптер описывает физический путь, которым работа доходит до конкретной программы. Программы у вендоров устроены по-разному, поэтому и пути разные. Один общий адаптер был бы враньём: он обещал бы запуск там, где запустить нечем.

От чего зависитПримерЧто меняется в адаптере
Есть ли у программы режим без интерактива — команда, которой её можно запустить с заданиемУ Codex есть codex exec, у Gemini — agy -p. У Cursor консольной команды нет — это редакторЕсть команда → kind: cli или headless. Нет → manual: работа ждёт во входящих, пока владелец сам не откроет программу
Как программой обычно пользуютсяClaude Code и Cursor — открытые сессии, где работает человек: они читают входящие сами, когда живутmanual и session: interactive. У Claude при этом есть claude -p, поэтому headless: ["claude"] указан: ведущий Codex может запустить его на задачу
Решение владельца, а не свойство программыПлатный агент сам по событию не стартует. У Codex и Gemini запуск возможен, но enabled: false (решения от 10 и 15 сентября)Очередь сначала, запуск только вручную. Набор не начинает платную работу сам
Что провереноУ Grok и MiniMax команда запуска есть, но живой вызов ни разу не доходил до концаmanual с headless, без автозапуска и без запуска на ревью, пока нет проб

Что адаптер не определяет. Роль, уровень модели и права агента адаптер не задаёт: роли и состав выбирает владелец в мастере, уровни лежат в models.json, а «может ли агент быть ревьюером» зависит от отдельного поля review_launch. Адаптер отвечает на один вопрос: как до этой программы дотянуться.

Почему адаптеры лежат только во встроенном каталоге. Адаптер решает, может ли набор запустить процесс на машине. Если бы его можно было объявить в проекте, репозиторий мог бы заставить набор выполнить любую команду. Поэтому проектный agents.json адаптер изменить не может: объявленный там игнорируется, и набор пишет предупреждение. Нового вендора добавляют в каталог набора после разведки vendor-probe, а не в проекте.

Как подключить нового вендора: collab в его настройки

Коротко: у вендора в каталоге (collab/config/agents.json) добавляется одно поле adapter.mcp_registration, и дальше установщик сам вписывает collab в файл настроек этого вендора, а панель по тому же описанию показывает его MCP-серверы. Кода под вендора писать не нужно.

"mcp_registration": {
  "kind": "json-file",                  // или "toml-file"
  "config_path": "~/.vendor/mcp.json",  // внутри домашнего каталога, без ..
  "servers_key": "mcpServers",          // таблица серверов; для вложенной — через точку
  "entry_extra": { "disabled": false }, // необязательно: простые поля записи (строка, число, true/false)
  "verify": { "argv": ["vendor", "mcp", "list"], "expect": "collab" }  // необязательно
}
  • Когда пишется: при установке, но только у того, чья программа есть на машине или чей каталог настроек уже существует. Для программы, которой нет, файл не создаётся.
  • Как безопасно: перед правкой делается копия, остальные настройки вендора не трогаются, повторный запуск ничего не меняет. Если установка не дошла до конца, запись откатывается вместе с ней; отдельная команда --rollback переключает релиз и настройки вендора не трогает (так же, как у остальных клиентов). Если задана проверка verify (только команда вендора вида <вендор> mcp …), после записи она запускается, и провал отменяет установку.
  • Один файл — один писатель: если два вендора (или вендор и клиент, которого установщик пишет сам) указывают один файл, установка останавливается с названием обоих. «Есть ли у вендора свой каталог» считается по каталогу вендора, а не по общему (~/.config, домашний каталог): иначе файл появился бы у вендора, которого здесь нет.
  • Чего поле не умеет: запись всегда в виде command + args + env. Вендор, у которого запись устроена иначе (например command списком и environment), этим способом не подключается и остаётся ручным.
  • Чего поле не касается: Claude, Codex, Gemini и Cursor установщик регистрирует своим кодом, для них поле отклоняется: у файла не должно быть двух писателей.
  • Вендор не из каталога: принимается как адаптер машины через --adopt-profile (см. выше); панель показывает его серверы так же.
  • Другие MCP-серверы (не collab): на вкладке «Набор → MCP-серверы» у каждого сервера в колонке «Добавить другим» — готовые команды для терминала, по одной на вендора, у которого этого сервера ещё нет (Claude Code, Codex, Gemini, Cursor). Значения ключей в них — ВАШ_КЛЮЧ: свой ключ человек подставляет сам; аргументы, похожие на секрет, тоже заменены. Для Codex с заголовками и для Cursor команда дописывает запись в их файл настроек, Cursor не перезаписывает сервер с тем же именем. Серверы, встроенные в приложение другого вендора (программа внутри *.app/Contents/, например node_repl и computer-use у Codex), и серверы, которым нужен рабочий каталог (cwd), не предлагаются: в другом агенте они не запустятся.
  • MCP-сервер только для одного проекта: файл ~/.agent-collab-kit/projects/<id>/mcp.json — { "servers": { "tracker": { "type": "http", "url": "https://mcp.example.com/mcp/my-org" } } }. Установщик регистрирует такой сервер в Claude Code на уровне local из каждого корня проекта и в каждом каталоге настроек: агент видит его только в папке проекта, в репозиторий ничего не пишется. Принимаются только http-серверы с https-адресом без логина, query и fragment (вход через браузер, /mcp); headers, env и имя collab отклоняются до любых изменений. Снимает установщик только то, что ставил сам (учёт — ~/.agent-collab-kit/state/project-mcp.json); одноимённый сервер, добавленный руками, остаётся. Codex, Gemini и Cursor хранят проектные настройки внутри репозитория, поэтому для них такой сервер не ставится — установщик пишет об этом строкой.

Панель и тесты

Панель (collab ui, код в ui/) — страница в браузере над теми же данными, что и CLI.

  • server.mjs — HTTP-сервер на 127.0.0.1 с токеном в адресе; views.mjs — функции «журнал → JSON» для экранов; setup-wizard.mjs — логика мастера настройки; public/ — страница, стили, скрипт и это руководство. Статические файлы (в том числе руководство) отдаются без токена.
  • Безопасность: только 127.0.0.1; токен; проверки Host и Origin; CSP default-src 'self' (поэтому стили только в файле, без встроенных); текст журнала пишут агенты, поэтому на страницу он выводится как текст, а не как разметка.
  • Что панель пишет: состав машины (мастер), задачу «уборка мелочей», закрытие и возврат задач владельцем — и только если она запущена из терминала владельца. Одобрений панель не выдаёт никогда: она показывает задачу, причину и команду, которую владелец выполняет в терминале.

Как поддерживать это руководство

У руководства две копии с одним содержанием:

  • Эта страница (ui/public/guide.html в репозитории набора) — основная. Её отдаёт панель (пункт «Руководство» в меню), она открывается и прямо из клона, поэтому читать её можно до установки.
  • Документ в Claude Docs — agent-collab-kit — руководство разработчика. Его удобно отправлять ссылкой тем, у кого нет набора; чтобы они его открыли, владелец делится документом через Share.

Обе копии обновляются вместе с релизом: коммит, который меняет описанное здесь, не считается законченным, пока нужный раздел не поправлен в обеих. Если они разойдутся, верна страница из репозитория.
