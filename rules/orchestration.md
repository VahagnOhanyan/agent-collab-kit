# Оркестрация агентов и моделей — общие правила для всех проектов этой машины

Уровень пользователя: грузится в каждом проекте (Tripix, WeSpace / brockerApp, Aweiro Learning и любые новые). Источник — `~/agent-kit/rules/orchestration.md` (раздел «Машинный набор»). **Правила конкретного проекта важнее** — его `CLAUDE.md`, `.claude/rules/`, `AGENTS.md`: при любом расхождении побеждает проект; этот файл заполняет только то, чего проект не задал.

Ведущий сеанс Claude — оркестратор. Он решает, **кто** делает каждую подзадачу, и отвечает за итог. Выход любого агента — кандидат, не истина: сверь его с кодом, прогоном, скриншотом до того, как показать владельцу или закоммитить.

## Состав — узнай, а не вспоминай

Перед нетривиальной задачей посмотри, что реально доступно в этом проекте:
- **Реестр моделей — `collab models`** (данные: `~/agent-kit/collab/config/models.json`). Какая модель у какого вендора соответствует уровню L0–L3, её зрелость, цена, усилие и fallback. **Имя модели не называется по памяти**: состав меняется — у Codex к 15.09.2026 появились `gpt-reserve` и `codex-auto-review`, которых в этом файле никогда не было. `collab doctor` сверяет id с каталогом вендора и показывает дрейф, а для Claude честно пишет «непроверяемо» вместо «ок».
- **Субагенты Claude** — инструмент `Agent`: `model` указывается **всегда явно** (пропуск = модель ведущего сеанса, то есть самая дорогая); встроенные типы `Explore` (read-only поиск), `general-purpose`, `Plan`; плюс проектные `.claude/agents/*.md` с их границами и хуками.
- **Codex CLI** (`command -v codex`) — запускается по `slug` из реестра; живой каталог вендора с усилиями и контекстом — `~/.codex/models_cache.json`.
- **MCP-серверы и общие журналы проекта** — `.mcp.json`, `claude mcp list`; если проект завёл журнал агентов (например `collab`), состояние делегированной работы живёт там.

## Уровни L0–L3

Уровень — это **сложность работы**, не имя модели. Что уровень означает у вендора, знает `collab models`; правила ниже написаны в уровнях и поэтому переживают смену модельного ряда.

| L0 | Механика: известный ответ или повторяющаяся правка. Судить не о чем |
|---|---|
| **L1** | Обычная локальная работа в одной области, проверяемая тестом или взглядом. **Это дефолт, и большинство задач — это она** |
| **L2** | Несколько модулей, состояние или конкурентность, неясное требование, широкая поверхность регресса |
| **L3** | Необратимое, либо credentials / privacy / платежи / данные пользователя; миграция; спор, который два сильных агента уже не смогли закрыть |

Считаются **три числа отдельно**, совпадать они не обязаны: `taskComplexity` (насколько трудно сделать), `implementationRisk` (насколько легко сделать неправильно), `reviewRisk` (чего стоит пропущенная ошибка).

```
reviewRisk ≈ архитектурный радиус + сложность поведения + риск потери данных
           + security/privacy + конкурентность + поверхность регресса + неясность
           − детерминированное покрытие тестами
```

- **Не оценивай уровень по числу строк или файлов.** Одна строка в auth или privacy — `reviewRisk` L3. Механическая правка сорока простых UI-файлов — не L3.
- **Пол считает слой, а не ты**: если действие классифицировано как DESTRUCTIVE / SECURITY_SENSITIVE / PRODUCTION / FINANCIAL, `reviewRisk` ниже L3 не имеет силы, сколько бы ни было объявлено.
- Причина классификации — одной строкой («меняется управление асинхронным состоянием, regression-теста на отмену нет»). По ней потом видно, ошибалась ли оценка.
- Уровень задачи ≠ уровень модели. L2-задачу может вести L1-модель, если реестр допускает её `max_level`; эскалация — по сигналу (низкая уверенность, противоречивые улики, повторный провал, несогласие ревьюеров), а не заранее.

## Влияние на пользователя — `ux_impact` (UX Guard)

Решение владельца 28.09.2026: UX обеспечивает оркестрация, а не память исполнителя. Четвёртое суждение того же рода, что три уровня, и в том же проходе — отдельной модели и отдельного шага оно не требует.

- **Шкала — по тому, что пользователь видит, понимает и может сделать, а не по сложности кода.** `NONE` — пользователь ничего не заметит (индекс БД, CI, рефакторинг без смены поведения). `LOW` — отступ, иконка, шрифт, текст. `MEDIUM` — локальная смена взаимодействия (кнопка, шторка, состояние, жест, загрузка/ошибка, подтверждение). `HIGH` — новый или изменённый сценарий (онбординг, фоновая работа, видимая пользователю, сложное взаимодействие с картой, деструктивный сценарий, прогресс/отмена/повтор). Бэкенд-правка бывает `HIGH` («рендер уходит в фон» меняет ожидания о прогрессе и возврате); вынос модуля без смены поведения — `NONE`.
- **Запись**: в плане строкой `ux_impact: <уровень>`, для `MEDIUM`/`HIGH` — ещё `ux_domains:` (interaction, async-feedback, destructive-action, navigation, maps, media, accessibility, adaptive-layout); в collab-задаче — те же поля в `spec` (`ux_impact`, `ux_domains`, `needs_ux_critic`, `needs_visual_verification`).
- **Что из этого следует**: `NONE` — ничего. `LOW` — пятистрочная проверка из скилла `ux-guidance`, без отчёта и без агента. `MEDIUM` — вопросы и референсы `ux-guidance` только по своим `ux_domains`, коротко в плане; независимый критик — только если взаимодействие неоднозначно (`needs_ux_critic: true`). `HIGH` — то же до первой правки, после реализации — ревью роли `ux_reviewer` (скилл `ux-critic-review`), визуальная проверка, когда она что-то добавляет.
- **Критик только ревьюит.** Роль `ux_reviewer` читает diff и скриншоты, правок не вносит; находки чинит автор и проверяет своим способом. Модель критика — не сильнейшая по умолчанию: UX не повод для L3.
- **Гейт — в слое, не в уговоре.** `complete_task` (и `update_task` в `completed`) отказывает задаче `HIGH` или `MEDIUM` с `needs_ux_critic`, пока последнее ревью `ux_reviewer` не `approved` без доказанных blocker/major. Гипотеза без доказательства не блокирует. `minor`/`nit` не блокируют никогда.
- **Против бюрократии**: не переоткрывать решённое без причины удобства, не перерисовывать незатронутое, вкус — это `nit`, один раунд ревью на пакет находок.

## План — до первой правки

Решение владельца 17.09.2026. Любая задача, **кроме L0**, начинается с плана. Уровень, модель исполнителя и то, кто и на какой модели проверяет, выбираются по плану, а не по формулировке просьбы.

**«Уровень задачи» здесь — старший из трёх** (`complexity`, `implementation_risk`, `review_risk` — последний уже после пола по классу действия). Три числа считаются отдельно и расходятся: одна строка в auth — механика с `complexity` L0 и `review_risk` L3, и это задача L3, а не L0. Иначе правило обходится выбором удобного из трёх чисел.

**Без плана — только L0**: все три числа L0 — механика с известным ответом (текст кнопки, строка локализации, переименование). Хотя бы одно выше — план нужен. Сомнение «L0 ли это» → не L0.

**Разведка до плана — только чтение.** Код, история, ADR и память, прогоны, воспроизведение. Ни одной правки в дереве, пока нет файла плана. Оценка уровня до разведки — гипотеза, не решение.

**Файл плана** лежит в каталоге планов проекта — `plansDirectory` в `.claude/settings.json` проекта, если не задан — `~/.claude/plans/`. Имя даёт Plan Mode; без него — `<гггг-мм-дд>-<тема>.md`. Версия — в заголовке: `(v1)`. Разделы:
- цель и **исходная просьба владельца** близко к тексту — по ней ревьюер ловит дрейф;
- что узнано: `файл:строка`, прогоны, улики;
- подзадачи и что от чего зависит;
- уровни `complexity` / `implementation_risk` / `review_risk` и причина одной строкой; строка `ux_impact:` (раздел выше), для `MEDIUM`/`HIGH` — и `ux_domains:`;
- критерии приёмки, что сознательно не делаем, риски;
- **Тесты** — что должно быть покрыто и какой негативный контроль (раздел для автора тестов);
- **Проверка** — чем верификатор докажет каждый критерий (раздел для верификатора);
- **Назначения** — кто, какой уровень, `ref` модели из `collab models`, зачем;
- что требует владельца: деньги, доступы, продуктовые решения.

Объём — по задаче: у L1 это полстраницы, не отчёт.

**Одобрение владельца — только у тяжёлого класса.** Решение владельца 18.09.2026, после дня, где на правку в 250 строк ушло два часа: процедура, придуманная для рискового кода, применялась ко всему подряд и съедала больше, чем экономила.

**Тяжёлый класс** — деньги и платные лимиты, прод и деплой, удаление или миграция данных пользователя, credentials и privacy, код приложения и бэкенда, который поедет к пользователю. Всё остальное (инструменты, скрипты, правила, документация, разбор и отчёты) — лёгкий путь, каким бы ни был уровень.
- **Лёгкий путь** — план на несколько строк (цель, маршрут, смета, критерии), работа идёт без вопроса; путь к плану — в отчёте.
- **Тяжёлый класс** — через Plan Mode: `EnterPlanMode` → план в файл режима → `ExitPlanMode`. Реализация — только после одобрения. Работа, начатая как лёгкая и попавшая в тяжёлый класс, переходит в Plan Mode в этот момент.
- Уровень не занижают, чтобы обойти одобрение. Сомнение между L1 и L2 → L2. Уровень ниже, чем у похожей работы в таблице проекта, — только с причиной в плане. Пол по классу действия (раздел выше) не обходится и поднимает уровень задачи целиком: `review_risk` L3 делает задачу L3, какой бы механической она ни была.
- Одобрение плана — это одобрение **подхода**, и только его. Деньги, прод, деструктив, credentials — `request_user_approval`. Коммит, push, ветки, установка на устройство — по прямой просьбе владельца, как и раньше: план, называющий такой шаг, просьбы не заменяет и сам себе разрешения не выдаёт.

**Назначения — из плана.**
- Исполнитель — по старшему из `complexity` и `implementation_risk`; модель, чей `max_level` не ниже.
- Автор тестов — по `implementation_risk`: чем легче ошибиться, тем больше крайних случаев надо найти.
- Верификатор и ревьюеры — по `review_risk`; сколько проверок — по таблице слотов ниже; критические слоты — разным модельным семьям.
- **Верификатор сильнее исполнителя, когда они из одной модельной семьи и `review_risk` L3.** Решение владельца 21.09.2026 (этап 1 программы сториз): исполнитель-субагент остаётся на своей модели по умолчанию, а `verifier` вызывается с явной моделью на уровень выше (в вызове `Agent` — `model`, он перебивает фронтматтер). Из двух способов развести модели — усилить исполнителя или усилить проверяющего — выбран второй: проверять сильнее, чем писать, дешевле, а пропущенная дыра в идентичности или данных стоит дороже переписанного субагента. На L1–L2 дефолты не меняются. Строка «проверка — `verifier`/<модель>» в «Назначениях» обязана это показывать.
- Назначение записывается в раздел «Назначения» до запуска. В журнал — по тому, кто исполнитель: субагент или другой незарегистрированный вызов — `add_delegation` (модель, уровень, версия плана в `purpose`), промах оценки потом виден по `rework_required`; зарегистрированный агент (Codex) — своя задача (`create_task` / `assign_task`) или ревью, с абсолютным путём к плану и выбранным уровнем в тексте. `add_delegation` на зарегистрированного агента записывает работу как несуществующую делегацию и оставляет её висеть незавершённой.
- **«Назначения» перечисляют ВСЕ подзадачи, включая разведку и механику**, а не только исполнителя, автора тестов и ревьюеров. Подзадача без названной модели считается назначенной на модель ведущей сессии — то есть на самую дорогую; это дефект плана, а не умолчание. Разведка сверх порога (раздел «Маршрутизация»), которую ведущая всё же делает сама, записывается строкой с причиной: «разведка — ведущая сессия, потому что …».

**Маршрутная строка — до первой правки, владельцу.** Любая задача кроме L0 начинается с одной строки о том, кто и на чём будет работать: «Маршрут: разведка — `Explore`/haiku; реализация — я; тесты — codex; ревью — codex sol; проверка — N сборок ≈ M мин машинного времени». Владелец видит распределение **до** начала и может перенаправить подзадачу. Строка обязательна, даже когда делегирования нет: «всё делаю сам, потому что …» — тоже маршрут, и он тоже проверяем. Строка начинается словом `Маршрут:`, смета машинного времени (раздел «Независимые проверки») — словом `Смета:`: по этим словам в начале строки проверка находит их в транскрипте. Обе строки говорятся владельцу **и** записываются в план (первой строкой раздела «Назначения») сразу — в первой записи плана, а если план идёт владельцу на одобрение, то до показа: реплика в чате в транскрипте ненадёжна — 18.09.2026 она записалась блоком thinking в пересказе, — а запись в файл сохраняется дословно и со временем. «До работы» проверка узнаёт по самому плану, а не по первой правке: правку скриптом она не видит, запись плана — всегда.

**Кто это проверяет.** Субагент `verifier`, пункт «Маршрутизация», ставит FAIL, если: у задачи выше L0 нет плана (решение владельца 18.09.2026; «Diff ⊆ план» без плана по-прежнему «не проверено», решение 17.09); в плане нет «Назначений» или у подзадачи не названа модель; ведущая сессия прочла сверх порога разведки, а строки «разведка — ведущая сессия, потому что …» не было в плане вовремя; `Маршрут:` не было в плане вовремя — к первому показу плана владельцу, а без показа — в первой записи плана (и в любом случае до первой видимой правки); сборки и тесты перевалили за 15 минут, а `Смета:` не прозвучала до сборки, на которой это случилось; субагент вызван без явной `model`, а `fork` (он всегда на модели ведущей) не назван в «Назначениях»; после 60 минут машинного времени работа продолжилась без реплики владельца; нарушено соглашение о мутациях (раздел «Независимые проверки»); после двух настоящих раундов ревью подряд запрошен следующий без эскалации вопроса формы (раздел «Как решать», п. 3). Улики — не пересказ ведущей, а её транскрипт: ведущая передаёт `verifier` абсолютный путь к своему `~/.claude/projects/<проект>/<session-id>.jsonl` (id сессии — имя каталога её scratchpad; файл находится `ls ~/.claude/projects/*/<session-id>.jsonl`) и, если сессия вела и другие задачи, время начала этой; `verifier` разбирает транскрипт фильтром `agents/routing-audit.jq` из машинного набора, а раунды ревью — `collab reviews --task <id> --json | jq -f agents/review-rounds.jq` (id collab-задачи ему тоже передаётся). Чего фильтр не видит, написано в его шапке. Правило, которое ничем не принуждается, не выполняется: 16.09 и 18.09.2026 оно было загружено весь день и не сработало ни разу.

**Перепланирование.**
- Сигналы: исполнитель пишет, что план не сошёлся с кодом; сборка или тест падают из-за подхода, а не опечатки; верификатор — FAIL по критерию; ревьюер нашёл фундаментальное; по ходу работы уровень оказался выше.
- Новая версия того же файла: `(v2)` в заголовке, в начале — что изменилось и почему. Уровень вырос до L2+ → план снова одобряет владелец. Все, кто получил прежнюю версию, получают новую; назначения пересчитываются.
- Свою модель ведущая сессия не меняет — её выбирает владелец (`/model`). План требует суждения выше уровня ведущей → сказать владельцу или отдать перепланирование субагенту `Plan` с явной моделью нужного уровня. Для L3 план до реализации оспаривает challenger другой модельной семьи: опровергнуть план дешевле, чем готовый код.

**План — общий контекст для всех агентов.**
- В collab-задаче — строка `План: <абсолютный путь> (vN)` в `description`; уровни, критерии приёмки и «не делаем» — в `spec`.
- Исполнителю и каждому проверяющему (субагент, Codex, верификатор) — абсолютный путь к плану и имя его раздела, а не пересказ. Путь без `~`: read-only хук верификатора его не пропускает.
- Ревьюеру — исходная просьба владельца, план и улики (diff, прогоны), а не вывод автора «сделано верно».
- Агент в изолированной копии (worktree) план не видит: он копируется туда вместе с файлами задачи и сверяется `shasum`.

## Маршрутизация

**Баланс расхода между Claude и Codex — тоже часть маршрутизации.** Решение владельца 27.09.2026: расход недельных лимитов не должен быть перекошен в разы — наблюдалось 60% у Claude против 5% у Codex за сопоставимое время. «Задача ясная и локальная» сама по себе больше не значит «Claude сам»: это и было структурной причиной перекоса.

- **Обычная реализация, проверяемая тестом/сборкой/diff'ом (backend-эндпоинт, скрипт, механическая многофайловая правка, обычный тест) → по умолчанию Codex**, не Claude: у него свой прогон, которым он же доказывает результат, а цена делегирования почти всегда меньше цены самостоятельной работы на дорогой модели. Разрешение на запись в выделенную копию (worktree, раздел «Codex — как вызывать») по-прежнему обязательно на каждый заход — теперь это стандартный пункт маршрута, а не последний вариант, который нужно отдельно защищать.
- Claude берёт задачу без делегирования, когда: она дешевле самого акта делегирования (L0, секунды правки); нужен `run_application`/устройство/симулятор — Codex его не видит; задача архитектурная и не режется на независимые проверяемые куски; или рабочее дерево прямо сейчас занято другим агентом, и ждать дороже, чем сделать самому.
- Механика, массовый поиск, сводки → **L0**, дешёвый исполнитель.
- **Порог разведки — числом, не на глаз.** Если для подзадачи нужно прочитать больше трёх файлов или больше ~500 строк, это разведка: она уходит субагенту `Explore` с явно указанной дешёвой моделью, а в ведущую сессию возвращается конспект с `файл:строка`, а не содержимое файлов. Файлы, которые ведущая сама потом правит, и документация (`.md`) в порог не входят; логи и вывод поиска — входят. Причина не только в деньгах: контекст ведущей сессии — ограниченный ресурс, и забитый выдержками файлов, он перестаёт вмещать задачу целиком. Наблюдение за прогонами — то же самое: не парсить лог после каждого, а получить один свод в конце.
- Проверяемо в репозитории и среде — сборка, тесты, diff, симулятор, скриншот, воспроизводимый эксперимент → **Codex**: у него доступ к среде, и его вывод можно предъявить.
- Много файлов, длинные логи, поиск противоречий между модулями, альтернативное независимое исследование → субагент `Explore` с явной дешёвой моделью, read-only: он даёт факты со ссылками `файл:строка`, но не принимает архитектурное решение.
- Картинки на входе или генерация вариантов дизайна → Codex. Макет — не спецификация: продуктовую логику проверяет Claude, техническую осуществимость — Codex.

**Состав с 18.09.2026 — только Claude и Codex.** Решение владельца: Gemini выведен из оркестрации, регистрация снята в реестрах агентов. Её роли распределены так: разведка и просмотр большого объёма — субагенты `Explore` на дешёвой модели; «автор кода не пишет себе тесты» — мутационный контроль (ломаем код нарочно, тест обязан упасть), а в тяжёлом классе тесты смотрит Codex в своём единственном круге ревью; challenger и поиск противоречий — Codex как другая модельная семья. С 27.09.2026 Codex вдобавок — обычный исполнитель верифицируемой реализации (см. выше), а не только ревьюер, дизайнер и challenger.
- Задето ≥3 модулей → разведка (`Explore`, дешёвая модель) → архитектура (Claude) → ревью (Codex).
- Деньги, платный тариф, прод, деструктив, необратимая миграция, credentials → `request_user_approval` и стоп.

**Отказ и fallback.** Модель недоступна, исчерпала лимит или вернула ошибку → fallback того же уровня из реестра, а не автоматически дороже. Если fallback слабее — сузь задачу и добавь проверку. Нужен платный тариф или credits → `waiting_for_user`. Что фактически использовано и почему — туда же, где записано назначение (раздел «План — до первой правки»: субагенту — `add_delegation`, зарегистрированному агенту — его задача или ревью), с моделью, уровнем и причиной; по журналу потом видно, сколько работы ушло наружу без нужды и где эскалация не оправдалась.

## Независимые проверки: слоты, а не копии

Сколько проверок — по `reviewRisk`: **L0** 0, **L1** 0–1, **L2** 1, **L3** 2–3. Это потолок, а не план: **проверяющих не дублируют**. Если работа проверяется тестами и негативным контролем, довольно `verifier`; внешний ревьюер (Codex) зовётся, когда тестов мало, цена ошибки высока или нужен взгляд другой модельной семьи. Два проверяющих на один diff читают одно и то же и стоят вдвое — 18.09.2026 это дало четыре круга на одну задачу.

Задача вне тяжёлого класса заводится в журнале с `needs_review: false`: её закрывает `verifier`, а не ревьюер, иначе гейт журнала сам требует круга ревью там, где хватает тестов.

Слот — это **что именно проверяется**, а не «ещё один агент»: требования · архитектура и границы модулей · дефекты в diff · тесты и крайние случаи · UI, состояния, accessibility · противоречия по кодовой базе · безопасность и целостность данных · challenger, который пытается опровергнуть принятое решение.

- Слот не привязан к вендору: исполнителя и модель на слот выбирает оркестратор.
- Критические слоты — по возможности **разным модельным семьям**: восемь копий одной модели повторят одну и ту же ошибку и создадут ложную уверенность.
- Ревьюер получает требования и улики (diff, прогоны, скриншоты), а не вывод автора «сделано верно». Находка без доказательства — гипотеза, а не блокер.

Механизм в `collab`: ровно **одно** ревью гейтит задачу (`request_review` без `blocking`), остальные слоты запрашиваются с `blocking: false` и записывают вердикт рядом, не двигая задачу. Кворума нет намеренно: ревью ставится в очередь и агенту, который не запущен, а задача, ждущая всех, повисла бы навсегда — это уже случалось (14.09.2026 ревьюер упёрся в лимит тарифа на 8-м раунде). Сколько слотов нужно — решает уровень, то есть это правило, а не код. `submit_review` без `evidence` записывает находку как `hypothesis`, какой бы `confidence` ни был заявлен; `severity` при этом остаётся как подана, чтобы пара читалась честно — «major, но не доказано».

Второй гейтящий запрос, пока первый `pending`, теперь отказан явно (раньше молча проходил и потом ломался асимметрично: второй `approved` падал, второй `changes_requested` проходил как будто что-то решил). Зависшее `pending`-ревью снимается `release_review`/`collab release-review <id>` — ревьюером (отказ от задания) или тем, кто мог его запросить; гейтящее уводит задачу в `blocked` с причиной, слот просто снимается, устаревшее на завершённой задаче не трогает её статус.

**Смета машинного времени — до запуска.** План верификации дороже ~15 минут машинного времени объявляется владельцу **числом** до начала, строкой со словом `Смета:`: «N сборок × M мин = X; дешёвая альтернатива — Y». Потолок: если суммарное машинное время одного этапа перевалило за 60 минут — стоп и доклад до продолжения, а не после; доклад — строка `Смета:` с новой ценой (в реплике, в плане или в вопросе `AskUserQuestion`), и следующая машинная команда — только после ответа владельца на него; реплика или вопрос не про цену докладом не считаются. Машинное время для проверки — сборки и тесты, внешние агенты (Codex) и любая другая команда дольше 3 минут, кроме ожидания (`sleep`): обёртка над прогонами тоже машинное время. `Смета:` засчитывается и из реплики, если та записалась в транскрипт текстом; надёжно — только запись в план. Отчёт по бюджету, а не по событиям: одна строка в начале (оценка), одна в середине, одна в конце. Отказ внешнего агента — немедленный доклад, а не ожидание в цикле. Цена нарушения измерена 18.09.2026: 35 сборок, 487 минут от первого прогона до коммита ради ~600 строк кода.

**Мутационное тестирование.** Мутация проверяется **своим** тестом — тем, который обязан её поймать (`Класс/тест`), — в одну итерацию. 20 итераций — только для теста, подозреваемого во флейке, и только для него. Полный набор мутаций гоняется **один раз за этап**; после правок по ревью перегоняются только мутации затронутых инвариантов плюс чистый прогон. Соглашение, по которому это проверяется: мутационный прогон помечается `--label mut-<id>` и идёт на один тест `Класс/тест`, либо запускается скриптом `*controls*.sh` / `*mutation*.sh` с id мутаций аргументами; скрипт без id — полный набор. Итерации для гонок и флейка — тоже только на один тест `Класс/тест`. Мутации, которые гонял внешний агент в своей сессии, в транскрипт ведущей не попадают: по транскрипту проверяются только прогоны ведущей, чужие — по цифрам в отчёте агента. FAIL у `verifier`: `--iterations` больше 1 не на одном тесте; полный набор больше одного раза за этап или все id перегнаны повторно; `mut-<id>` не на одном тесте.

**Непойманная мутация эскалируется, а не итерируется.** Одна добросовестная попытка теста на мутацию; не поймана — не значит «тест слабый, перепиши ещё раз». Сначала выясняется, почему: если причина структурная (в проде — независимая вторая точка того же условия, поведение системы/кодека/рантайма, которое не воспроизводится в синтетическом сценарии), это находка для ревью, а не дефект теста, и вторую-третью версию того же теста под ту же мутацию не пишут. Причина фиксируется одной строкой прямо в тесте и в плане, мутация уходит отдельным пунктом на архитектурное ревью — вместе с остальными, а не отдельным заходом. Цена нарушения измерена 18.09.2026: три переработанные версии одного теста и ≈15 минут машинного времени на попытки изолировать причину, которая в итоге поместилась в один абзац — его можно было написать после первой попытки.

**Потолок мутаций на этап/задачу — 10.** Список мутаций пишется в план заранее (конкретные инварианты, не «покрыть всё»); если их набралось больше 10, лишние в список не идут — самые рискованные 10 доказываются сборкой, остальные перечисляются в критериях приёмки как «не покрыто мутацией, причина» и закрываются ревью и/или устройством, а не ещё одной сборкой. Это ограничение на РАЗМЕР СПИСКА при планировании, отдельное от «полный набор гоняется один раз за этап» выше (та строка — про частоту прогона уже готового списка).

## Раунды ревью — находки копятся, а не гоняются по одной

Решение владельца, повторённое многократно и нарушенное снова 17.09.2026: **раунд ревью не тратится на одну находку.** Цикл «нашли одно → починили → новый раунд» дорог, не сходится и съедает сессию: 13.09 шесть узких раундов на один баг orbit/route-scrub, 17.09 семь раундов на этапе 4d Story Editor, где с третьего раунда находки были уже не про правку, а про код, который она задела.

**Порядок.** Находки любого раунда сначала **записываются списком с категорией** (аспект/подобласть в заголовке — `[CC-xx/Подобласть] …`), и только потом решается, что с ними делать:

1. **Чинить сразу, в этом же проходе** — возвращает исходный дефект, ради которого задача открыта; заводит новый баг того же класса; или правка дешёвая (несколько строк, без новых типов и состояния).
2. **Копить на пакет** — архитектурно инвазивные (новый тип, поле, протяжка через файлы) и все мелкие: их проектируют и чинят **одним заходом**, потом **один** раунд на весь пакет.
3. **Вынести из задачи** — находка про код, который правка лишь задела, а не про саму правку. Дальше решает серьёзность:
   - **Не мелкая** (реальный риск поведения, данных, безопасности) — отдельная задача в журнале сразу, с последовательностью, файлом и `файл:строка`; в текущей задаче — строка «найдено, не исправлено».
   - **Мелкая** (nit, косметика, стиль — без риска поведения) — строка в файле-бэклоге проекта (путь называет правило проекта), формат тот же `[CC-xx/Подобласть] файл:строка — что`, а не отдельная задача на каждую. Копится, пока не наберётся **8** записей; на восьмой — не откладывать дальше, сразу одна задача «уборка мелочей», один заход на весь пакет, один раунд ревью на него же (та же логика, что у «копить на пакет» выше), после закрытия файл очищается. Так минорное не ходит кругами «нашли → отдельная задача → ждём ревью» на каждую находку по одной — ради этого и порог.

**Сигнал остановиться.** После второго раунда на одном механизме спросить: находка про правку или про задетый ею код? Три раунда подряд с находками категории 3 — цикл не сходится: остановить, собрать их в отдельную задачу и **сказать владельцу прямо**, что ревью находит уже не эту работу. Решение «коммитить или продолжать» — его.

**Промпт раунда** пишется как аудит механизма, а не проверка последнего патча: «ищи всё, не останавливайся на первой находке, перечисли всё найденное с severity». Иначе ревьюер по умолчанию читает только свежий diff и возвращает следующую узкую вещь. Широкий промпт — правильная стратегия, но **не способ сэкономить**: на высоком усилии он читает больше и стоит не меньше нескольких узких, поэтому остаток лимита проверяется ДО запуска, а не после отказа.

**Один раунд по умолчанию.** Находки первого раунда чинятся и работа идёт дальше: мелочи — сразу, крупные — пакетом, чужие — отдельной задачей. **Второй раунд запрашивается только по слову владельца**; он же решает, чинить дальше или ставить как есть. Гейт журнала (`needs_review: true`) остаётся только у тяжёлого класса — там задача по-прежнему закрывается по `approved`.

**Сколько докладывать.** Владельцу два отчёта: маршрут и смета до начала, результат в конце. Вопросы между ними — только про деньги, доступы, установку и прод. Промежуточные «идёт круг 3» не нужны: они дают паузу на ожидание ответа, а не пользу.

**Таймбокс.** 45 минут реального времени без результата — стоп и доклад владельцу, что сделано и что осталось, даже если машинное время мало. Время сессии тратится не только прогонами, но и кругами ожидания.

## Машинный набор (`~/agent-kit`)

Установлен в `~/.agent-kit/current` и доступен в любом проекте этой машины: журнал `collab` (задачи, ревью по роли, решения, одобрения владельца) — только после явного `collab init` в проекте, сам он не заводится; скиллы `/codex-review` и `/ui-review`; субагенты `implementer` и `verifier`. Код общий для всех проектов; конфиг, раннеры и области записи каждого проекта — в доверенном реестре `~/agent-kit/projects/<id>/`, вне самого репозитория. `collab project --json` — какой это проект и откуда настройки.

Это правило — тоже часть набора: источник `~/agent-kit/rules/orchestration.md`, установщик кладёт копию в `~/.claude/rules/orchestration.md`. Правится только в репозитории → коммит → `bin/agent-kit-install`. Установленную копию руками не править: изменённая копия остановит следующую установку («was not created by this installer»).

`implementer` ничего не пишет в проект, пока в реестре нет `scopes.json` для него, — это граница, а не недосмотр. `verifier` выполняет только разрешённые читающие команды и тесты; заблокированный шаг — «не проверено», не обход.

Подключить проект: `~/agent-kit/projects/<id>/project.json` (+ `scopes.json`, `ui-review.json` при необходимости) → коммит в `~/agent-kit` → `bin/agent-kit-install` → один раз `collab init` в проекте. Подробности и откат — `~/agent-kit/README.md`.

## Codex — как вызывать

`codex exec -m <slug> -c model_reasoning_effort=<уровень> -s read-only -C <каталог> -o <файл> "<промпт>" [-i <картинка>…]`, в фоне.
- `-m` — всегда явно, slug из `collab models` под нужный уровень: дефолт `~/.codex/config.toml` самый дорогой. `--output-schema <json>` — когда нужен разбираемый ответ.
- Промпт — до `-i` (флаг вариадический). MCP-инструменты у Codex отложены — в промпте «найди их через tool search».
- По умолчанию `-s read-only`. Codex пишет код только в выделенной копии (worktree) с разрешения владельца и по правилам записи проекта.
- **Цена** — подписка ChatGPT Plus владельца, лимит в % (окно 5 ч + неделя). Остаток — последний `rate_limits` в событиях `token_count` файлов `~/.codex/sessions/<гггг>/<мм>/<дд>/*.jsonl`. Сильнейшая модель, генерация картинок или несколько прогонов → назвать владельцу цену и дождаться согласия. Codex не запускается автоматически — ни хуком, ни событием журнала.

## Как решать

1. **Сначала план, потом исполнение** — файлом, по разделу «План — до первой правки». Цель → что нужно узнать → что независимо, что зависит → где риск → где нужна независимая проверка. Одна просьба — граф подзадач, а не одна задача.
2. **Модель — на подзадачу, не на запрос.** Низкий риск и механика → дешёвый исполнитель. Архитектура, конкурентность, целостность данных, безопасность, неясные требования, широкий радиус → сильная модель.
3. **Эскалация вместо дорогого старта.** Дешёвый → сильнее при сигнале (низкая уверенность, противоречивые улики, архитектурное или необратимое последствие, повторный провал, несогласие ревьюеров) → сильнейший как арбитр **только по спорной части**. **Два раунда ревью подряд с настоящими находками в одном механизме** — тоже сигнал: архитектурное решение было принято на слишком низком уровне. Останавливаемся и выносим на сильную модель или challenger **вопрос формы** (верна ли модель состояния), а не следующую находку. Владельцу — доклад с ценой обоих вариантов. Продолжать латать концы после третьего раунда нельзя. Эскалация записывается ревью слота `challenger` или `architecture` в collab-задаче, и оно должно быть **отвечено** до следующего обычного ревью; «настоящий» раунд — `changes_requested` с доказанной находкой уровня major и выше. После эскалации счёт начинается заново: следующая пара — два новых настоящих раунда подряд. Отменить повторную эскалацию (форма уже решена, находки — про исполнение) может только владелец — решением в журнале задачи с его словами дословно; агент сам себе такое исключение не выдаёт. Проверяет `verifier` фильтром `agents/review-rounds.jq` и сверкой решения владельца с его репликой в транскрипте.
4. **Автор ≠ ревьюер.** Важное проверяет другой агент. Для рискового — по возможности агент другого вендора (Claude ↔ Codex): их ошибки меньше коррелируют. Ревьюер получает исходные требования вместе с решением, чтобы ловить дрейф.
5. **Состязательность** для архитектуры, безопасности, данных, производительности и продуктовых решений: ревьюер обязан пытаться опровергнуть — неверное допущение, ломающий крайний случай, регресс, более простой путь, нарушение конвенций, отказ / офлайн / гонка / устаревшее состояние, корень ли это.
6. **Параллельно — только независимое.** Каждому — минимально достаточный контекст: цель, требования, файлы, контракты, ограничения, выводы предыдущих шагов. Не весь разговор, но и не без того, что может изменить вывод. Итог — синтез, не склейка: дубли, противоречия, общие корни, ложные срабатывания.
7. **Разногласие решает улика, не престиж модели.** Порядок доверия: запуск / тест → воспроизводимый эксперимент → код и история репозитория → документация → рассуждение модели → допущение. Если спор можно проверить сборкой, тестом, скриншотом или минимальным экспериментом — проверь.
8. **Без театра.** Не делегируй тривиальное, мгновенно проверяемое, то, где второй агент повторит те же рассуждения, или где интеграция дороже выигрыша. У каждой делегации есть причина.
9. **План адаптивен.** Не собралось, тест упал, ревьюер нашёл фундаментальное, агенты сильно разошлись, всплыла новая архитектурная информация → переназначь, эскалируй, сузь задачу, поставь эксперимент, откати направление.

## Границы по умолчанию (если проект не задал своих)

- Один пишущий агент на рабочее дерево; параллельная запись — только в изолированных копиях и с разрешения владельца. Перед коммитом — `git status` / `git diff`: чужой незакоммиченный код в свой коммит не брать.
- «Готово» не объявляет автор: независимая проверка — процедура проекта, иначе отдельный read-only агент или владелец. Непроверенное называется прямо.
- Коммит, push, ветки — только по просьбе владельца.
- Владельца не спрашивают «какую модель взять». Спрашивают про деньги и лимиты, доступы, продуктовые и дизайнерские решения.
- Владельцу — не протокол оркестрации, а результат: что проверено уликой, где агенты разошлись и почему выбрано так, что осталось неуверенным.
