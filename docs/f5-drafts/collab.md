# Слой совместной работы агентов (`collab`)

Общее состояние для AI-агентов, работающих над этим репозиторием: задачи, сообщения, ревью, решения, запросы одобрения и результаты проверок — в файлах, а не в чьём-то контексте. Решение и границы — [ADR-0011](../decisions/0011-multi-agent-collaboration-layer.md), переезд с машинную установку и новые гарантии — [ADR-0013](../decisions/0013-collab-moves-to-machine-level-agent-kit.md). Код общий для всех проектов машины — `~/agent-kit/collab/` (репозиторий-набор), Tripix пользуется **установленным релизом** `~/.agent-kit/current`, а не рабочим деревом набора. Конфиг и раннеры этого проекта — доверенный реестр `~/agent-kit/projects/tripix/`, вне самого репозитория.

Первые два агента — `claude` и `codex`. Третий добавляется записью в реестре; протокол не меняется.

---

## Архитектура

```
CLI (владелец)         MCP-сервер (агенты)         гейт и тесты
        └────────────────────┬────────────────────┘
                         api.mjs                    ← единственный фасад
   registry · tasks · messages · reviews · decisions · approvals · policy · runs
                         store.mjs                  ← версии, транзакции, аудит
                    .collab/ (файлы + лок)
```

Три понятия держатся раздельно и не смешиваются:

| Понятие | Что это | Где объявлено |
|---|---|---|
| **Агент** | независимый исполнитель | `~/agent-kit/collab/config/agents.json` (встроенное), `~/agent-kit/projects/tripix/collab/agents.json` (переопределение Tripix, целиком) |
| **Роль** | за что он отвечает | `~/agent-kit/collab/config/roles.json`, `~/agent-kit/projects/tripix/collab/roles.json` |
| **Способность** | что он физически умеет | `~/agent-kit/collab/config/capabilities.json`, `~/agent-kit/projects/tripix/collab/capabilities.json` |

Роль — это обещание. Гейт не пропустит агента, который держит роль, но не имеет требуемых ею способностей: такому агенту маршрутизировали бы работу, которую он не может выполнить.

## Состояние

Журнал живёт в корне, а не в рабочем дереве: **корень журнала — родитель git common dir**, поэтому у всех worktree одного репозитория (включая `.claude/worktrees/*`) один и тот же `.collab/`, а не по копии на дерево.

```
.collab/                    ← в .git/info/exclude общего common dir, не в отслеживаемых файлах
  journal.json              маркер: привязывает журнал к этому корню (пишет collab init)
  tasks/<id>.json  messages/<id>.json  reviews/<id>.json
  decisions/<id>.json  approvals/<id>.json  runs/<id>.json + <id>.log
  agents/<id>.json          рантайм-статус и heartbeat (НЕ конфиг)
  events.jsonl              append-only аудит: кто, что, когда
  locks/store.lock          единственный мьютекс на запись
```

**`.collab/` не появляется сам.** Единственный способ его завести — `collab init` в корне журнала; команда сама добавляет `.collab/` в исключения git (через common dir, ни один отслеживаемый файл не меняется) и пишет `journal.json` последним, атомарно, так что читатель видит либо журнала нет, либо журнал целый. Отслеживаемые, символьно-ссылочные, пустые или недостроенные `.collab/` отвергаются, как и маркер, привязанный к другому корню (журнал скопировали или перенесли).

Живой журнал Tripix старше этого маркера — он в формате `events.jsonl` + коллекции, но без `journal.json`. Реестр `~/agent-kit/projects/tripix/project.json` ставит `"legacy_journal": true`: владелец однократно ручается за markerless-журнал по этому корню. `collab init --adopt` (только владелец, только в интерактивном терминале, с повторным вводом корня) привязывает маркер, после чего флаг реестра можно снять.

Статический конфиг (кто **может** существовать) и рантайм (кто **работает**) — разные файлы. Смешать их значит превратить обозреваемый конфиг в изменяемую базу.

### Почему это надёжно

- **Чтение никогда не берёт лок.** Запись заменяется целиком через `rename(2)`, атомарный в пределах файловой системы, поэтому читатель видит либо старый файл, либо новый. Благодаря этому `collab status` отвечает даже когда писатель завис — а именно к нему и тянутся, когда что-то застряло.
- **Все записи сериализованы** одним файловым мьютексом (`open` с `O_CREAT|O_EXCL`), включая записи из разных процессов.
- **Между вызовами** мьютекс бесполезен: агент прочитал задачу, две минуты думал, пишет. Для этого `expected_version` — конфликт возвращается вместе с текущей записью, чтобы повтор не требовал второго чтения.
- **Протухший лок** снимается по двум условиям сразу (процесс мёртв **или** возраст выше порога), а снятие атомарно через `rename`: из двух одновременных «сносителей» выигрывает ровно один.
- **Ничего не висит вечно.** У claim'а есть аренда; истёкшая делает задачу снова доступной, и это видно **при чтении**, без демона и без того, чтобы что-то запускалось.

## Жизненный цикл задачи

```
created ──► assigned ──► in_progress ──► review ──┬─► approved ──► completed
   │            │             │                   │
   │            │             │                   └─► changes_requested ──┐
   │            │             │                                           │
   │            │             └───────────────◄───────────────────────────┘
   │            │
   └────────────┴──► waiting_for_user   (ждёт владельца)
                     waiting_for_agent  (ждёт ответа другого агента)
                     blocked            (всегда с причиной)
                     cancelled
```

Переходы заданы таблицей в `src/transitions.mjs`. Недопустимый переход — ошибка, в которой перечислено, куда перейти было можно. `completed` недостижим, если задача требует ревью, которое не одобрено, или если владелец не ответил на запрос одобрения.

`created → waiting_for_user` существует не по недосмотру: задачу, действие которой требует одобрения, **нельзя взять в работу** до ответа владельца, поэтому спросить нужно уметь раньше, чем у неё появится владелец.

## Протокол

**Сообщение** адресуется агенту, роли или способности. В записи хранится **селектор**, а не готовый список получателей: получатели вычисляются при чтении инбокса по текущему реестру. Поэтому выдача агенту роли `code_reviewer` делает видимыми уже отправленные письма этой роли. ⛔ «Очевидная» оптимизация — резолвить при отправке и хранить массив — молча ломает это свойство.

Типы: `question`, `answer`, `review_request`, `review_response`, `task_assignment`, `task_update`, `blocking_issue`, `decision_request`, `decision`, `completion`, `clarification`.

**Ревью** запрашивается по роли, а не по имени. Автор структурно исключён из кандидатов — не «попросили быть честным», а не может быть выбран. `changes_requested` без находок отвергается. Раунды нумеруются; цикл повторяется столько раз, сколько нужно.

**Решение и разногласие.** Две разные позиции переводят решение в `disputed`, и закрыть его не может ни один из спорящих — иначе выигрывал бы тот, кто сказал последним. Остаётся `escalate_decision` к владельцу. Позиция без обоснования отвергается: это не голосование.

Решение, обязательное для всех, живёт в [`docs/decisions/`](../decisions/), а не здесь. Запись в collab — рабочая заметка, которая заканчивается полем `adr_ref`.

## Одобрение владельца

Классы действий и то, требуют ли они владельца, — в `collab/config/policy.json` (встроенное) и его переопределении `~/agent-kit/projects/tripix/collab/policy.json` — проект может только ужесточать классификацию, кроме правил с `lowers_default: true` и обоснованием:

| Класс | Владелец нужен |
|---|---|
| `READ_ONLY`, `SAFE_WRITE` | нет |
| `EXTERNAL_SIDE_EFFECT`, `DESTRUCTIVE`, `SECURITY_SENSITIVE`, `PRODUCTION`, `FINANCIAL` | да |

Оцениваются **все** правила, побеждает **максимальная серьёзность**. Порядок строк ничего не решает — иначе перестановка строки в JSON молча понижала бы правило. Действие, не совпавшее ни с чем, попадает в класс, требующий одобрения: классификатор, который fail-open, ничего не классифицирует.

Грант **одноразовый** и привязан к отпечатку действия: разрешение купить одно не разрешает купить другое, и повторно использовать его нельзя.

### ⛔ Честная граница

Оба агента работают под одним пользователем, с шеллом. **Это не граница безопасности против решительного процесса.** Полная модель угроз и то, что не исправлено и почему, — `~/agent-kit/collab/SECURITY.md`. Что слой действительно обеспечивает:

1. Обычного пути нет — **ни один MCP-инструмент не выдаёт одобрение**, и `collab check-config` проверяет это по реальному списку инструментов.
2. CLI отказывается разрешать, когда выставлен `COLLAB_AGENT_ID` (он есть в любом шелле агента). Снять переменную — сознательный шаг, видимый в истории.
3. Требуется интерактивный терминал и повторный ввод id заявки — против реальной ошибки, не против злоумышленника.
4. Каждое разрешение пишет `pid`, `ppid`, `tty` в аудит: подделанный грант не невидим.
5. **Конфиг и раннеры приходят только из доверенного реестра** (`~/agent-kit/projects/<id>/`), сопоставленного по корню журнала — ни из `.mcp.json` этого репозитория, ни из окружения.
6. **Окружение — не вход.** `COLLAB_CONFIG_DIR`, `COLLAB_REGISTRY_DIR`, `COLLAB_PROJECT_ROOT`, `COLLAB_STATE_DIR` игнорируются и репортятся (`collab doctor` их называет).
7. **Журнал не появляется сам и не принимается чужой.** Только `collab init` создаёt `.collab/`; отслеживаемый, символьно-ссылочный или скопированный/перенесённый журнал отвергается, markerless legacy — только по явному флагу реестра.

**Настоящее принуждение** для опасного действия должно стоять в харнессе, вне досягаемости агента: `permissions.deny` в `.claude/settings.json` и `PreToolUse`-хук по образцу `scripts/claude-hooks/push-gate.py`. Это отдельная работа, и она не сделана.

## Проверки как общий ресурс

`~/agent-kit/projects/tripix/collab/runners.json` — allowlist Tripix с фиксированным argv, без `sh -c` (переопределяет встроенный `~/agent-kit/collab/config/runners.json` целиком). Аргумент-путь проверяется на каталог, шаблон и существование.

`preflight` · `backend-lint` · `backend-architecture` · `backend-tests` (пофайлово) · `web-tests` · `web-typecheck` · `rail-tests` · `rail-typecheck` · `ios-build` (`build-for-testing`, симулятор не бутится). Раннера `collab-tests` больше нет: тесты самого слоя — часть набора, живут в `~/agent-kit` и не запускаются из проекта.

Результат — общая запись: ревьюер читает прогон автора, а не повторяет его. Разбираются **счётчики TAP**, а не только exit code: набор, который весь пропустился, выходит с нулём и ничего не доказывает.

Не допускаются никогда и почему — в `runners.json`, поле `refused`.

## Git

Слой координирует намерение, а не файловую систему. `claim_files` отвергает пересечение с чужим живым claim'ом и называет задачу и владельца. `collab status` показывает грязные файлы, которые **не заявлены ни одной задачей**, — это чужой WIP, и относиться к нему как к своему значит затереть работу.

Ветки и worktree остаются как в [`.claude/rules/workflow.md`](../../.claude/rules/workflow.md); push — только ведущий сеанс после зелёного preflight, это держит `push-gate.py`, и collab туда не лезет.

## Команды владельца

```bash
collab status                                   # кто над чем работает, что ждёт, как выглядит дерево
collab task <id>                                # задача с её ревью и перепиской
collab inbox codex                              # что адресовано агенту
collab approvals                                # что ждёт лично вас
collab approve <id>                             # только интерактивный терминал
collab reject <id> --note "..."
collab decide <id> <исход> --why "..." --adr docs/decisions/00NN-....md
collab log --tail 40                            # аудит
collab doctor                                   # агенты, адаптеры, чего не хватает и как починить
collab brief codex                              # что агент читает о себе
collab project --json                           # какой проект, корень журнала, откуда конфиг — ничего не пишет
```

`collab` установлен на `PATH` установщиком набора (`bin/agent-kit-install`, симлинк на `~/.agent-kit/current/bin/collab`) и работает из любого каталога внутри дерева Tripix, включая worktree.

## Пример: полный цикл

```
Claude   create_task «разобрать реестр MCP-инструментов»       → created,   класс READ_ONLY
Claude   claim_task + claim_files                              → in_progress
Claude   request_review(role: "code_reviewer")                 → review, реестр выбрал codex
Codex    get_messages → видит review_request со scope
Codex    submit_review(changes_requested, findings: [...])     → changes_requested
Claude   правит, update_task                                   → in_progress
Claude   request_review(role: "code_reviewer")                 → review, раунд 2
Codex    submit_review(approved, «проверил каждый throw»)      → approved
Claude   complete_task                                          → completed
```

Вся цепочка остаётся в `events.jsonl`. Имя `codex` не прозвучало ни в одном вызове.

## Пример: нужно одобрение

```
Codex    create_task «добавить живые данные по рейсам»
         action: «buy a subscription to the flight data API»   → класс FINANCIAL
Codex    claim_task                                             → отказ: APPROVAL_REQUIRED
Codex    request_user_approval(cost_estimate: "~$49/мес")       → задача в waiting_for_user
         ⏸ здесь всё останавливается: инструмента, который выдаёт грант, нет
Владелец collab approvals
Владелец collab approve apr_...                                 → TTY, ввод id заявки
         granted → задача возвращается в пул и теперь может быть взята
```

Отказ переводит задачу в `blocked` с формулировкой владельца как причиной.

## Добавить агента

1. Запись в `~/agent-kit/projects/tripix/collab/agents.json` (переопределяет одноимённый встроенный файл целиком): `id`, `provider`, `roles`, `capabilities`, `briefing`, `briefing_file`. Без `adapter` — адаптеры решают, может ли слой стартовать процесс, поэтому берутся только из встроенного `~/agent-kit/collab/config/agents.json`; объявленный в реестре проекта был бы проигнорирован.
2. Новая роль, если нужна, — в `~/agent-kit/projects/tripix/collab/roles.json` (со списком требуемых способностей).
3. Файл брифинга — `~/agent-kit/projects/tripix/collab/briefings/<id>.md` (путь относителен каталогу `collab/` этого проекта в реестре).
4. Регистрация MCP-сервера у этого агента с его `COLLAB_AGENT_ID` — для Codex это делает `bin/agent-kit-install`, для другого клиента вручную по образцу `~/agent-kit/collab/codex/config.snippet.toml`.
5. `bin/collab check-config --project tripix` (из `~/agent-kit`) — скажет про опечатку в роли или способности и покажет правила `lowers_default`, если они есть.
6. `bin/agent-kit-install` — правка реестра вступает в силу только после установки.

Ни одной правки в протоколе.

## Codex

MCP-сервер регистрируется в `~/.codex/config.toml` установщиком набора (`bin/agent-kit-install`, идемпотентно, с бэкапом); исходный блок для ручной сверки — `~/agent-kit/collab/codex/config.snippet.toml`, установка сама указывает его на установленный релиз `~/.agent-kit/current`, а не на рабочее дерево набора. `AGENTS.md` в Tripix — симлинк на `CLAUDE.md`, так что поведенческие правила Codex читает те же. Персональный брифинг Tripix — `~/agent-kit/projects/tripix/collab/briefings/codex.md` (переопределяет встроенный `~/agent-kit/collab/config/briefings/codex.md`), возвращается его собственным `whoami`.

## Если что-то не так

| Симптом | Что смотреть |
|---|---|
| MCP-сервер не поднялся | `COLLAB_AGENT_ID` не задан или не зарегистрирован в `agents.json` — сервер выходит с кодом 2 и пишет причину в stderr |
| Инструментов `collab` нет в сессии | новый MCP-сервер виден только после перезапуска клиента |
| `NOT_INITIALIZED` | в этом корне ещё нет журнала — `collab init` (или `collab project --json`, чтобы увидеть, какой корень вообще резолвится) |
| `JOURNAL_INVALID` | `.collab/` есть, но не журнал: отслеживается git'ом, символьная ссылка, недостроен, либо маркер привязан к другому корню (скопирован/перенесён) — причина в тексте ошибки; для собственного перенесённого журнала — `collab init --adopt` |
| `LOCK_TIMEOUT` | в сообщении назван держатель (агент и pid). Если процесса нет, лок снимется сам по возрасту |
| Задача «залипла» на исчезнувшем агенте | `collab sweep`, либо просто `collab tasks --all` — освобождение опортунистическое |
| `PATH_CONFLICT` | файлы заявлены другой живой задачей; в ошибке её id и владелец |
| `doctor` пишет `unavailable` | в той же строке — точная команда, которая это чинит |
| Прогон «зелёный», но ничего не проверил | смотрите `result.headline`: `NOTHING RAN — N skipped` |
| Непонятно, откуда взялся конфиг | `collab project --json` — журнал, worktree, откуда конфиг (встроенный/реестр), реестр, игнорируемые переменные окружения |

## Тесты

```bash
node --test collab/test/       # весь набор (~2 мин: часть тестов поднимает реальные процессы), из ~/agent-kit
bin/collab check-config        # встроенные дефолты и все проекты реестра, включая Tripix
```

Что доказано: мьютекс держит шесть настоящих процессов (и негативный контроль показывает, что без него апдейты теряются); конфликт версий; протухший лок снимается ровно одним; полный цикл ревью с повтором; своё ревью невозможно; одобрение блокирует завершение и не переиспользуется; секрет в сообщении отвергается до записи; два процесса на одной задаче — ровно один победитель; исчезнувший агент не запирает работу; MCP-handshake настоящими байтами; ни один инструмент не выдаёт одобрение; журнал не заводится неявно и не принимает чужой маркер.
